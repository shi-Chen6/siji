📖 故事线：从“搭网页”到“守住 Web”

零基础学 Web 应用安全，先建立整体地图：网页是用 HTML/CSS/ASP 搭出来的（模块一），用户状态靠 Cookie/会话维持（模块二）；攻击者最爱的两个突破口是 XSS（往页面塞脚本）和 CSRF（借你身份发请求）（模块三、四）；根因常在“输入没验证”导致 SQL 注入（模块五）；代码不严谨还会出目录遍历、缓冲溢出等洞（模块六）；最后终端和浏览器也要硬（模块七）。7 个模块一路学下来，45 题全拿下。

生活类比：做网站安全像开连锁店——先懂货架怎么搭（基础）、给会员发卡（Cookie）、防有人在留言板贴恶毒纸条（XSS）、防捡到门禁卡冒领（CSRF）、收货要安检（输入验证）、仓库门别乱给钥匙（安全编码）、店员也要体检（终端）。少一环都不稳。

1模块1 Web 技术基础（HTML/CSS/ASP）

学 Web 安全前，先懂网页是怎么搭的。HTML 是网页的骨架（标记语言），CSS 是皮肤（样式），ASP 等脚本是大脑（服务端动态生成页面）。

常见 HTML 标记：a 做锚点/链接，table/tr/th/td 画表格（td 是数据单元格、rowspan 跨行、colspan 跨列），表单控件 type 决定长相（submit、button、reset 是按钮，password 是密码框）。

外部样式表用 link 标签引入（不是 style 标签内写，也不是 style 属性行内）。ASP 里 Response.Cookies 是只写的（服务器种、客户端读），Application 对象全局共享、可做网站计数器。

这些基础零件，是后面讲“改页面、偷 Cookie、塞脚本”等攻击的前提——不懂零件，就看不到漏洞在哪。

类比：生活类比：网页像一间店面——HTML 是货架和标牌（结构），CSS 是装修（样式），ASP 是后台仓管（动态出数据）。黑客要搞破坏，先得知道货架怎么摆、标牌怎么改。

2模块2 Cookie 与会话管理安全

Cookie 是网站存在你浏览器里的小纸条，记着“你是谁、登录了没”。三类：Session Cookie（关浏览器即删）、Secure Cookie（只走 HTTPS 防偷看）、HTTP-Only（禁止 JS 读取，防 XSS 偷走）。

注意坑：Cookie 内容可加密（含用户 ID、有效时间），但“加密”不等于“安全”——Secure 是走 HTTPS 不是 HTTP；HTTP-Only 才是防脚本偷。

会话管理要安全：会话数据存/传要加密、登录成功建新会话（防会话固定）、避免 CSRF、合理存活时间超时销毁并清信息。漏洞扫描系统会专门查 Cookie 注入、XSS、Cookie 有效性。

类比：生活类比：Cookie 像商场给的会员卡——Session 卡离店作废，Secure 卡只在加密通道递（防被人瞄到），HTTP-Only 卡不让售货员（JS）乱看。卡上信息加密了，但被明文递送照样丢人。
【自测】通过（ ）可清除上网痕迹。
选项：A.禁用脚本　B.禁止 SSL　C.清除 Cookie　D.查看 ActiveX 控件
▸ 显示解析
选 C。清除 Cookie 可清除上网痕迹（登录态、浏览偏好等存在 Cookie 里）。Cookie 记录登录状态、浏览痕迹；清除它等于“退出并擦掉痕迹”。禁用脚本、禁止 SSL、查看 ActiveX 都不直接清痕迹。问“清除上网痕迹”，Cookie 是痕迹载体，清它最直接；其余三项不相关。上网痕迹在 Cookie，清除它就擦掉。
【自测】下列关于 HTTP Cookie 说法错误的是（ ）。
选项：A.Cookie 总是保存在客户端中　B.Session Cookie 只是在用户使用站点期间存在，一个 WEB 浏览器会在退出时删除 Session Cookie　C.Secure Cookie 是指 Cookie 有 secure 属性，只能通过 HTTP 使用　D.在支持 HTTP-Only 属性的浏览器中，HTTP-Only Cookie 只有在传输 HTTP/HTTPS 请求时才能被使用，这样可限制被其他的非 HTTP API 访问（如 JavaScript）
▸ 显示解析
选 C。错误项：Secure Cookie“只能通过 HTTP 使用”——实际 Secure 是“只经 HTTPS（加密）传输”，不是 HTTP。Cookie 类型：Session Cookie 会话期存在、退出删；Secure Cookie 带 secure 属性，仅通过 HTTPS 加密传输（防窃听）；HTTP-Only 限制 JS 访问防 XSS 偷。C 把 Secure 说成“只能 HTTP”错（应是 HTTPS）。找“说法错误”，C 错（Secure=HTTPS 而非 HTTP）；A/B/D 正确。Secure 走 HTTPS 不是 HTTP，HTTP-Only 防 JS 偷。

3模块3 跨站脚本攻击 XSS

XSS（跨站脚本）是攻击者把恶意脚本塞进网页，别的用户一打开就中招。存储型最狠：脏数据存进数据库，所有访客都被执行。

防 XSS 靠三招：输入白名单验证、输出净化（转义）、特殊字符过滤。关键坑：参数化查询防的是 SQL 注入，不是 XSS！

XSS 危害 = 网站挂马、盗各类账号、窃商业资料；它动不了数据库（那是 SQL 注入的活）。

类比：生活类比：XSS 像坏人在公共留言板写“看到此条自动转账”的纸条，店员（浏览器）不懂，照念给每个顾客听。存储型是把纸条贴进总台账，人人都中招。
【自测】下列（ ）能最好的描述存储型跨站脚本漏洞。
选项：A.不可信任数据通过不可靠的源直接进入 Web 服务器，然后在客户端浏览器显示给用户　B.不可信任数据直接在客户端的 JavaScript 中处理，然后直接在客户端显示　C.不可信任数据包含在动态内容中的数据在没有经过安全检测就存储到数据库中提供给其他用户使用　D.不可信任数据没有任何处理，直接在客户端显示
▸ 显示解析
选 C。存储型 XSS：不可信数据未经安全检测就“存进数据库”，再发给其他用户显示。XSS 三类：反射型（数据进服务器再回显客户端）、存储型（数据存库，别人访问时取出执行）、DOM 型（纯前端 JS）。题干“存储到数据中提供给其他用户”正是存储型。关键词“存储到数据/其他用户使用”=存储型，对应 C；A 偏反射型表述，B/D 不涉存储。存储型 XSS：入库再害人；反射型：即时回显。
【自测】下列方法（ ）不能有效地防止跨站脚本。
选项：A.验证输入的数据类型是否正确　B.使用参数化查询方式　C.对输出数据进行净化　D.使用白名单对输入数据进行验证
▸ 显示解析
选 B。不能有效防 XSS 的是“使用参数化查询”——参数化查询防的是 SQL 注入，不是 XSS。XSS 是“输出到页面时未转义/输入未过滤”；防 XSS 靠输入白名单、输出净化、特殊字符过滤。参数化查询解决的是 SQL 注入（把数据与命令分离），对 XSS 无效。问“不能防 XSS”，B 参数化查询针对 SQL 注入，选它；A/C/D 都是 XSS 防御手段。参数化查询防 SQL 注入，不防 XSS。
【自测】由于跨站脚本攻击漏洞而造成的危害的是（ ）（多选）
选项：A.网站挂马　B.盗窃企业重要的具有商业价值的资料　C.盗取各类用户账号　D.访问未授权的页面和资源
▸ 显示解析
选 ABC。XSS 危害：网站挂马、窃商业资料、盗各类账号；“访问未授权页面资源”更多是越权/CSRF，不单列 XSS 典型危害。XSS 偷 Cookie/劫持会话→挂马、盗号、窃密；D 的“查看修改删除数据库”是 SQL 注入或服务端漏洞后果，非 XSS 直接造成。问“XSS 造成的危害”，D 不属 XSS 典型，排除；A/B/C 是。XSS 害：挂马、盗号、窃密；删库是注入。
【自测】下列危害中，（ ）不是由跨站脚本攻击造成的。
选项：A.盗窃企业重要的具有商业价值的资料　B.网站挂马　C.盗取各类用户账号，如机器登录账号、用户网银账号、各类管理员账号等　D.查看、修改或删除数据库条目和表
▸ 显示解析
选 D。XSS 不造成的危害是“查看/修改/删除数据库条目和表”——那是 SQL 注入或服务端越权。XSS 在客户端偷 Cookie/挂马/盗号，动不了数据库；改库是 SQL 注入（把恶意 SQL 拼进查询）。D 选它。问“不是 XSS 造成”，A/B/C 都是 XSS 危害，D 是注入危害，选 D。XSS 动不了库，删库是注入的活。
【自测】下列选项中，（ ）不能有效地防止跨站脚本漏洞。
选项：A.使用白名单的方法　B.使用参数化查询　C.对系统输出进行处理　D.对特殊字符进行过滤
▸ 显示解析
选 B。不能有效防 XSS 的是“使用参数化查询”（防的是 SQL 注入）。同 Q28：参数化查询隔离 SQL 命令与数据，治注入；XSS 要输入过滤+输出转义。B 对 XSS 无效。问“不能防 XSS”，B 参数化查询治注入不选 XSS；A/C/D 是 XSS 防御。参数化查询治注入，不治 XSS（同 Q28）。

4模块4 跨站请求伪造 CSRF

CSRF（跨站请求伪造）是“借你已登录的身份发请求”：你登录网银没退出，点开坏网页，它就以你权限转账。

会话持续越久，被 CSRF 概率越大；用 POST 只是稍难一点；多步提交也不可靠（可发多个请求模拟）。

防御：重要操作前要求额外信息（验证码/二次确认）、用一次性令牌（token）、限制认证 Cookie 的到期时间。

类比：生活类比：CSRF 像有人拿着你忘退的门禁卡，去前台说“帮我转笔钱”——前台认卡不认人。短时效卡 + 每次额外口令（token）就能防。
【自测】下列关于跨站请求伪造的说法正确的是（ ）（多选）
选项：A.只要你登陆一个站点 A 且没有退出，则任何页面都可发送一些你有权限执行的请求并执行　B.站点 A 的会话持续的时间越长，受到跨站请求伪造攻击的概率就越大　C.目标站点的功能采用 GET 还是 POST 并不重要，只不过 POST 只是加大了一点点跨站请求伪造的难度而已　D.有时候复杂的表单采用多步提交的方式防止跨站请求伪造攻击其实并不可靠，因为可以发送多个请求来模拟多步提交
▸ 显示解析
选 ABCD。CSRF 说法全对：登录未退可被冒用、会话越长越危险、GET/POST 不重要、多步提交也不可靠。CSRF 是“借你已登录的身份发请求”：你登录 A 没退出，别的页面就能以你权限发请求；会话久则窗口长；POST 只是稍难；多步提交可多发请求模拟。四项描述均符合 CSRF 原理，全选。CSRF 借身份：未退可被用、越久越险、POST 稍难、多步可破。
【自测】下列措施中，（ ）能帮助减少跨站请求伪造（多选）
选项：A.执行重要业务之前，要求用户提交额外的信息　B.对用户输出进行处理　C.使用一次性令牌　D.限制身份认证 cookie 的到期时间
▸ 显示解析
选 ACD。减少 CSRF：重要业务前额外验证、一次性令牌、限制认证 Cookie 时限；“对用户输出处理”是防 XSS 不是防 CSRF。CSRF 防御：①重要操作加二次确认/验证码（额外信息）；②一次性令牌（token）防重放；③缩短认证 Cookie 有效期减少窗口。对“输出”处理针对 XSS。B 是输出处理（XSS 范畴），不防 CSRF，排除；其余三项防 CSRF。防 CSRF：二次验证 + 一次性令牌 + 短 Cookie；输出处理防 XSS。

5模块5 SQL 注入与输入验证

SQL 注入是脏数据拼进数据库命令，根因 = 没验证输入。安全编码要对输入做四查：长度、类型、特殊字符、数值范围，且先规范化再验证。

数据库权限按最小化给（应用账号只拿必需权限），降低被注入后的破坏面。

因“未验证输入”引起的漏洞：缓冲区溢出、跨站脚本、SQL 注入（信息泄漏成因更广，不直接对应）。

类比：生活类比：输入验证像快递收件安检——量尺寸（长度）、看品类（类型）、查违禁品（特殊字符）、核重量（范围）。不安检，炸弹（注入）就进库。
【自测】在安全编码中，需要对用户输入进行输入处理，下列处理中（ ）是输入处理（多选）
选项：A.选择合适的数据验证方式　B.建立错误信息保护机制　C.限制返回给客户的信息　D.对输入内容进行规范化处理后再进行验证
▸ 显示解析
选 AD。安全编码的输入处理：选合适验证方式、先规范化再验证；建错误保护、限返回信息属“输出/错误处理”非输入处理。输入处理聚焦“进来时”：选验证方式（白/黑名单）、规范化（统一编码）后再校验。错误信息保护、限制返回是输出侧。B/C 是输出/错误处理，不属“输入处理”，排除；A/D 是输入侧。输入处理：选验证 + 先规范化；错误保护属输出。
【自测】应根据情况综合采用多种输入验证的方法，以下输入验证方法需要采用（ ）（多选）
选项：A.检查数据是否符合期望的长度　B.检查数据是否符合期望的类型　C.检查数据是否包含特殊字符　D.检查数据是否符合期望的数值范围
▸ 显示解析
选 ABCD。输入验证应综合：长度、类型、特殊字符、数值范围都查。健壮输入验证多维度：长度（防超长）、类型（数字/字符）、特殊字符（防注入）、数值范围（防越界）。四者都用。四项都是输入验证方法，全选。验证四查：长度、类型、特殊字符、范围。
【自测】下列属于输入验证方法的是（ ）（多选）
选项：A.检查数值数据是否符合期望的数值范围　B.检查数据是否包含特殊字符　C.检查数据是否符合期望的类型　D.检查数据是否符合期望的长度
▸ 显示解析
选 ABCD。输入验证方法：数值范围、特殊字符、类型、长度都查（与 Q19 同理）。同 Q19：长度、类型、特殊字符、数值范围四维度验证，全选。四项皆验证手段，全选。验证四查：范围、特殊字符、类型、长度。
【自测】（ ）漏洞是由于没有对输入数据进行验证而引起的（多选）
选项：A.缓冲区溢出　B.信息泄漏　C.跨站脚本　D.SQL 注入
▸ 显示解析
选 ACD。未对输入验证引起的漏洞：缓冲溢出、跨站脚本、SQL 注入；信息泄漏不一定由“未验证输入”直接造成。不校验输入→恶意数据进系统：超长触发缓冲溢出、特殊字符触发 XSS、注入串触发 SQL 注入。信息泄漏成因更广（配置/逻辑），非仅输入未验。问“因未验证输入”，A/C/D 都由脏输入触发；B 信息泄漏不直接对应。未验输入→溢出、XSS、SQL 注入。
【自测】在安全编码中，应该按照（ ）为应用程序分配数据库访问权限。
选项：A.最大化原则　B.优先原则　C.最小化原则　D.随意原则
▸ 显示解析
选 C。安全编码按“最小化原则”分配数据库权限（够用最少，不滥权）。权限最小化：应用账号只拿必需权限（如仅某库读写），降低被注入后破坏面。最大化、随意都危险。问“分配权限原则”，安全编码铁律是最小化，选 C。库权限最小化，够用就收。

6模块6 安全编码与典型漏洞

代码不严谨就出洞：把用户输入直接拼进文件路径（如 reports/ 加 rName 再 delete）会目录遍历，能删任意文件；字符串指针不限制长度会缓冲区溢出。

还有 URL 未授权访问（要按角色明确授权）、不安全加密存储（明文存密码，CSDN 事件）。写代码要校验、最小权限、加密存储。

类比：生活类比：路径拼接不校验，像让访客自己填“要删哪个文件”还直接执行——他说“../../机密”就删到根了。最小权限像只给仓库钥匙，不给大门钥匙。
【自测】以下代码存在（ ）漏洞。String rName = request.getParameter("reportName");File rFile = new File("/usr/local/apfr/reports/"+rName) ;rFile.delete();
选项：A.缓存区溢出　B.SQL 注入　C.跨站脚本　D.目录浏览
▸ 显示解析
选 D。代码把用户输入 rName 直接拼进路径并 delete，造成“目录浏览/路径遍历”漏洞（可删任意路径文件）。rFile = new File("/.../reports/"+rName) 未校验 rName，攻击者可传 ../../etc/passwd 之类越权访问/删除文件——属目录遍历（路径操纵）。题干选项给“目录浏览”。问漏洞类型，参数拼路径未过滤=目录浏览/路径遍历，非缓冲溢出、SQL 注入、跨站。路径拼接不校验=目录遍历，可越权删文件。
【自测】下列代码存在的漏洞是（ ）。 void func(char *str){}
选项：A.文件上传　B.跨站脚本　C.SQL 注入　D.缓存区溢出
▸ 显示解析
选 D。函数 func(char *str) 未限制长度就使用 str，典型“缓冲区溢出”风险（题中选项给缓存区溢出）。不检查输入长度直接拷/用字符串，超长会覆盖相邻内存——缓冲区溢出。代码虽空，考点是“未限定 str 长度”的溢出隐患。问漏洞，字符指针未限长=缓冲溢出，对应 D；A 文件上传、C 跨站、B 不相关。字符串未限长=缓冲区溢出。

7模块7 终端与浏览器安全延伸

Web 安全不只网站端，终端也要硬：服务器和客户端必须装公司统一部署的防病毒系统，覆盖全部。

病毒经文件共享、电子邮件、Web 网页、系统漏洞传播；禁活动脚本只能减网页脚本风险，挡不住本地程序执行；最新浏览器不等于防黑客（只是少已知漏洞）；合规要求浏览器不低于 IE9。

Oracle 客户端连接工具用 SQL*PLUS 与 PL/SQL Developer（IE 浏览器不是）。

类比：生活类比：网站是店，终端是店员——店员电脑中毒，店也保不住。防病毒是全员工装，浏览器升级只是换双好鞋，不等于穿了防弹衣。
【自测】管理信息系统的各类服务器及接入网络的计算机必须安装公司统一部署的（ ），要求覆盖所有服务器及客户端。
选项：A.网页浏览器软件　B.防病毒系统　C.远程控制系统　D.即时通信系统
▸ 显示解析
选 B。服务器和客户端必须安装公司统一部署的“防病毒系统”，覆盖全部。终端/服务器安全防护基础动作是装防病毒软件并统一管理；浏览器、远程控制、即时通信都不是“必须统一部署”的安全底座。问“必须安装”且“覆盖所有服务器及客户端”的安全软件，防病毒系统最贴切。全网必装防病毒，统一管控。
【自测】禁止使用活动脚本可以防范 IE 执行本地任意程序。（判断）
选项：A.正确　B.错误
▸ 显示解析
选 错误。仅“禁止活动脚本”不足以防范 IE 执行本地任意程序——还要限制本地文件、ActiveX 等。活动脚本（如 JavaScript）只是一类执行途径；禁止它能减少网页脚本风险，但本地程序执行还涉及 ActiveX、本地文件权限等，单靠禁脚本不够。说法太绝对（说“可以防范”），禁脚本只是措施之一，不能杜绝本地任意程序执行。禁脚本不够，本地执行还靠多道闸。
【自测】使用最新版本的网页浏览器软件可以防御黑客攻击。（判断）
选项：A.正确　B.错误
▸ 显示解析
选 错误。用最新浏览器不能“防御黑客攻击”——新浏览器只是少已知漏洞，黑客攻击靠多层防护。升级浏览器只是减少自身漏洞，但攻击面还在（插件、社会工程、服务器漏洞等），单靠新版浏览器挡不住黑客。说法绝对，浏览器新不等于安全，错误。新浏览器不等于防黑客，只是少洞。
【自测】根据相关规定，在进行计算机终端初始化配置工作时，要求所配置浏览器为（ ）或以上版本。
选项：A.IE9　B.IE10　C.IE11　D.IE8
▸ 显示解析
选 A。初始化配置要求浏览器为 IE9 或以上版本。合规配置基线规定终端浏览器不低于 IE9（旧版漏洞多），故最低 IE9。问“或以上版本”，取最低要求 IE9。浏览器最低 IE9，旧版有洞。
【自测】降低计算机病毒的影响范围就必须有效的控制计算机病毒的传播途径，下列属于计算机病毒传播途径的是（ ）（多选）
选项：A.通过文件共享传播　B.通过电子邮件传播　C.通过 WEB 网页传播　D.通过系统漏洞传播
▸ 显示解析
选 ABCD。病毒传播途径：文件共享、电子邮件、Web 网页、系统漏洞都能传。病毒靠各种载体扩散：共享文件、邮件附件、网页挂马、系统漏洞主动侵入。四者皆是途径。四项都属传播途径，全选。病毒四路：共享、邮件、网页、漏洞。
【自测】请选择以下那几项是 oracle 客户端的链接工具：（ ）（多选）
选项：A.IE 浏览器　B.SQL*PLUS　C.PL/SQL Developer　D.以上答案均不对
▸ 显示解析
选 ABC。Oracle 客户端连接工具：IE 浏览器不是（IE 是上网用），SQL*PLUS 与 PL/SQL Developer 是。连 Oracle 数据库的客户端工具常见 SQL*PLUS（命令行）、PL/SQL Developer（图形）；IE 是网页浏览器，不连库。D“以上均不对”与事实反。问“连接工具”，排除 IE（浏览器），选 SQL*PLUS、PL/SQL Developer。连 Oracle 用 SQL*PLUS、PL/SQL Developer，IE 不行。

🃏 速查卡：Web 应用安全 45 题核心

① Web 基础

  • type=password 是密码框；submit/button/reset 是按钮
  • rowspan 跨行、colspan 跨列；td 是单元格
  • 锚点用 a；外部样式表用 link；Response.Cookies 只写、Application 计数器

② Cookie/会话

  • Session 退出删、Secure 走 HTTPS、HTTP-Only 防 JS 偷
  • 会话四要：安全存传、登录换、防 CSRF、超时清

③ XSS

  • 存储型入库再害人；防靠输入白名单+输出净化+过滤
  • 参数化查询防 SQL 注入，不防 XSS
  • XSS 害：挂马/盗号/窃密；动不了库

④ CSRF

  • 借登录身份发请求；防御：二次验证+一次性令牌+短 Cookie

⑤ 输入验证

  • 四查：长度/类型/特殊字符/范围；先规范化再验证
  • 库权限最小化；未验输入→溢出/XSS/SQL 注入

⑥ 安全编码

  • 路径拼接不校验=目录遍历；字符串不限长=缓冲溢出
  • URL 按角色授权；密码加密存储（别明文）

⑦ 终端/浏览器

  • 全网必装防病毒；病毒四路：共享/邮件/网页/漏洞
  • 禁脚本不够；新浏览器不等于防黑客；浏览器最低 IE9
  • Oracle 客户端：SQL*PLUS、PL/SQL Developer
